# Orchestration

How the orchestration session runs the engineering loop: cut tickets, start implementing sessions, review, integrate. Read this when you are that session; implementing sessions follow `.claude/skills/implement-ticket/SKILL.md` instead.

## Cut tickets

1. Work from a `ready` brief. Use `to-tickets`: slice into issues sized to one fresh context, each with Brief, Requirements, Area, Test seams, Done when, and blocking links. Two tickets that run in parallel touch different areas; shared contracts go first as their own ticket. Before showing the breakdown, check that every field, id, code and default a ticket's tests will assert is named in a brief; one that is not gets its planning pass first, since an unnamed shape becomes an inbox entry, a wait at the merge gate and a planning commit on the branch. Before folding a small item into a ticket, search the open issues for it (`gh issue list --search`): a rule two tickets both carry holds the second one's merge. The breakdown shows those names per ticket with the brief that names each, and a size estimate; a ticket that would change more than about 500 lines is two tickets, split before the owner approves. A check that needs the running app is a live check: the implementing session drives the real window with Playwright (the live-check harness, `docs/agents/live-checks.md`), answering native dialogs and drops from the test, and puts its screenshots in the pull request. Only a check that needs the owner's own judgment is marked "owner check" and is the owner's at merge.
2. Show the owner the breakdown (titles, areas, blockers) for approval, then publish every issue with the `ready-for-agent` label. The owner does not approve individual issue bodies.

## Start implementing sessions

- One session per unblocked ticket, each in its own git worktree, never in the integration checkout.
- The prompt is short: "Implement issue #n with the `implement-ticket` skill", plus anything the issue cannot carry (a merged PR to build on, a decision from the owner).
- Start the next unblocked `ready-for-agent` tickets as slots free, about four implementing sessions at once, without asking the owner.
- Archive a session you started once its pull request has merged; never delete one.

## Review a pull request

Docket runs the merge review on the owner's machine (ADR 0030): it reviews each head whose CI passed with the reviewers `.claude/review.json` names, against the `REVIEW.md` rubric, verifies their findings, posts them as a review on the pull request, and runs the merge gate. A pull request gets no other review: the implementing session checks its plan's assumptions before coding (`implement-ticket` step 2) and leaves the diff to Docket. Docket's page (`http://127.0.0.1:4477`) shows its queue and running reviews; its README, in the Docket repository (`KPandaK/docket`), says how it decides what is due, retries and cancels. Each round:

1. The implementing session polls Docket for its own pull request and fixes what the review posts (`implement-ticket` step 5); forward nothing to it while it does. Read its end-of-turn report and relay to the owner only what it escalates: a decision `CLAUDE.md` leaves to the owner, a defect that keeps coming back, Docket or CI not running, or a pull request no session owns. Name a defect's cause to the owner only once the `assumption-checker` has read the code for it: the symptom alone names the wrong one. A session whose pull request waits on a planning pass messages you when it stops: run the pass at once (Resolve inbox entries): settle each entry as `CLAUDE.md` (Decide the details) says, record the call in the brief's Changes line, and take to the owner only an entry that rule leaves to them. Only when a session is not polling its pull request (its turn ended before the review posted), send it every finding of the round in one message: a second message queues behind the session's turn and may never be read.
2. To see where any pull request stands, ask Docket (`curl -sS http://127.0.0.1:4477/pulls/<n>`); never poll GitHub for it.
3. Past five fix rounds (Docket's `review.maxRounds`), Docket marks the pull request as waiting on the owner, but the session keeps fixing while each round finds new defects (`implement-ticket` step 5). Merging with a blocking finding open stays the owner's call.

## Resolve inbox entries

The merge gate holds a pull request while its inbox has an open entry (ADR 0025): its review is clean but its status stays pending, naming the entries. Planning commits for a pull request go onto its branch, which is checked out in the implementer's worktree; a separate planning pull request costs a review, a queue merge and a merge of main on the ticket's branch, and is made only for a shape two in-flight tickets share, which must land on `main` once. Whoever opens one drives it to merge as `implement-ticket` steps 4 to 6 drive a ticket's pull request. A brief's "Built so far" follows `docs/briefs/README.md`: it rides the ticket's branch, never a pull request that merges ahead of the code. Use a detached worktree:

1. `git worktree add --detach ../ersa-plan origin/<branch>`, then `node scripts/role.mjs planning` inside it.
2. `git merge origin/main` if the branch is behind. Briefs, `docs/MANIFEST.md` and the ADR index merge with the union driver (`.gitattributes`), so two planning commits adding a Changes line or a requirement keep both; read the merged section once, then regenerate the manifest.
3. Update the briefs as `docs/briefs/README.md` (Changing a brief) says, delete the resolved inbox lines, run `node scripts/manifest.mjs --check`, commit, `git push origin HEAD:<branch>`. When the pass adds or retires a requirement ID the ticket builds, edit the issue's Requirements list in the same step (`gh issue edit <n> --body-file`): the spec check runs on the IDs the issue lists, and fails every round on a retired one. When the pass adds or changes a requirement the branch's code does not meet yet, mark the pull request a draft before you push (`gh pr ready <n> --undo`): Docket skips a draft, so it reviews no head whose requirement is still unbuilt.
4. Tell the implementing session the pass is pushed, naming each requirement it added or changed: the session pulls, builds and cites them, marks a draft ready, and waits on Docket for the new head (`implement-ticket` step 6). Remove the worktree when done.

## Merge

- Docket adds a clean head to the merge queue when the gate passes: CI green, no open inbox entry, nothing pushed after the review but clean merges of `main`. The queue builds and tests the merge before `main` moves and merges with a merge commit, so `Implements:` trailers stay (ADR 0030); a branch behind main needs no merge of main first. A head the queue removes (CI failed on the merge, or a conflict) needs a push, and CI and the review run again. Docket sets the `Merge review` status on a head; on the queue's merge commit a check of the same name (the `Merge review (queue)` workflow) passes only when that pull request's head carries a successful status, so the ruleset can require it.
- A clean pull request that changes an owner-only path (`gate.ownerPaths` in `.claude/review.json`: workflows, hooks, instruction files, the review config and rubric, the manifest, the merge queue's check) is labeled for the owner, who merges it. So is a bot's pull request (a dependency bump), without a review, since taking a new version is the owner's call (ADR 0015). One labeled `hold` is reviewed and never enqueued, and Docket turns off auto-merge armed on a held or unreviewed head. The label does not take out a head Docket has already enqueued, so ask Docket for the state before you report a pull request as held, and tell the owner at once when it is queued.
- After a merge, `git pull` in the integration checkout and report to the owner in a few lines, listing the calls agents made on it, so the owner can overrule one.
- When a batch's last ticket merges, run the live checks on `main` (`docs/agents/live-checks.md`) and file what fails: a ticket runs only the live checks it finds reading what it changes, so one it missed can be stale. Then cut one more ticket: a retirement ticket for the surface the batch replaced (a control moved elsewhere, a list a tree superseded), found by reading the batch's briefs' "Built so far" against the interface. Surface no ticket retires is what the owner finds by hand.

## Train the harness

Merges are automatic, so the harness is trained in batches. Run a pass in a planning session when the owner asks. When you report a merge, offer one if 10 or more pull requests have merged since the last pass and no pass's pull request is open (`gh pr list --author @me --search "Harness: lessons from in:title"`). The pass's steps are in `docs/agents/harness-lessons.md`; read it when you run one.
