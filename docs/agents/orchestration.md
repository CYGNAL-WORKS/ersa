# Orchestration

How the orchestration session runs the engineering loop: cut tickets, start implementing sessions, review, integrate. Read this when you are that session; implementing sessions follow `.claude/skills/implement-ticket/SKILL.md` instead.

## Cut tickets

1. Work from a `ready` brief. Use `to-tickets`: slice into issues sized to one fresh context, each with Brief, Requirements, Area, Test seams, Done when, and blocking links. Two tickets that run in parallel touch different areas; shared contracts go first as their own ticket. Before showing the breakdown, check that every field, id, code and default a ticket's tests will assert is named in a brief; one that is not gets its planning pass first, since an unnamed shape becomes an inbox entry, a wait at the merge gate and a planning commit on the branch. The breakdown shows those names per ticket with the brief that names each, and a size estimate; a ticket that would change more than about 500 lines is two tickets, split before the owner approves. Size alone does not decide the rounds a ticket takes (the fix cascades do, `review-pr` step 5), but every ticket over 1,000 lines has taken two rounds or more. A check that needs the running app is a live check: the implementing session drives the real window with Playwright (the live-check harness, `docs/agents/live-checks.md`), answering native dialogs and drops from the test, and puts its screenshots in the pull request. Only a check that needs the owner's own judgment is marked "owner check" and is the owner's at merge.
2. Show the owner the breakdown (titles, areas, blockers) for approval, then publish every issue with the `ready-for-agent` label. The owner does not approve individual issue bodies.

## Start implementing sessions

- One session per unblocked ticket, each in its own git worktree, never in the integration checkout.
- The prompt is short: "Implement issue #n with the `implement-ticket` skill", plus anything the issue cannot carry (a merged PR to build on, a decision from the owner).

## Review a pull request

The merge review runs on the owner's machine (ADR 0023). The merge review poller (`scripts/merge-review-watch.mjs`, run every 5 minutes by a scheduled task; its header says how to register the task and where its log is) runs the `review-pr` skill through `scripts/merge-review.mjs` on up to two heads at once among those whose CI passed, the head whose CI passed first leading, and posts the findings as a review on the pull request. The review runs the pull request's own tests as the owner, with the owner's `gh` login: only pull requests from this repository are reviewed, never a fork's. The head carries a "Merge review" commit status: pending while the review runs or while a clean head waits for the gate (GitHub still working out the merge, a CI rerun), red when a high or medium finding blocks the merge, and `error` when the run itself failed. The poller takes a pending head up again after an hour. An `error` is the owner's to look at: the log says why, and `node scripts/merge-review.mjs <n> --head <sha>` in a fresh detached worktree at that head runs the review again (either review checkout may hold a live review). The status is for people and the poller; the `main` ruleset must not require it, since the queue would wait for it on the merge commit, where nothing sets it. Each round:

1. The implementing session watches its own pull request and fixes what the review posts (`implement-ticket` step 4); forward nothing to it while it does. Read its end-of-turn report and relay to the owner only what it escalates: three rounds spent, `needs-owner`, a gate refusal, a planning pass needed, or a pull request no session owns. Only when a session is not watching its pull request (its turn ended before the review posted), send it every finding of the round in one message: a second message queues behind the session's turn and may never be read. When a head has waited over an hour for a verdict, read the poller's last log line (`.scratch/merge-review-watch.log`, or the terminal it runs in) and say what it waits for.
2. Run `review-pr` by hand only when asked, on `git diff origin/main...origin/<branch>`, in a detached worktree under `.scratch/`; reviewers never check out a branch in the integration checkout, and get what the skill's step 2 names, not the implementer's conclusions.
3. The implementing session fixes each finding with the smallest change; the skill's step 5 says when a fix is a new mechanism and becomes its own ticket. A mechanism kept because the pull request is unsafe without it is re-reviewed whole (the skill's step 6): #71's round-one stage reducer drew a high and then a medium in the next two rounds.
4. Stop after three fix rounds. If the third still finds a defect of medium severity or worse, take the choice to the owner (merge and follow up, or another round) rather than sending a fourth.

## Resolve inbox entries

The merge gate holds a pull request while its inbox has an open entry (ADR 0025): its review is clean but its status stays pending, naming the entries. Planning commits for a pull request go onto its branch, which is checked out in the implementer's worktree; a separate planning pull request costs a review, a queue merge and a merge of main on the ticket's branch, and is made only for a shape two in-flight tickets share, which must land on `main` once. Whoever opens one drives it as `implement-ticket` step 4 drives a ticket's pull request: `review-pr` before it opens, CI, the review, the fix rounds, and a turn that ends only when it merged or waits on the owner. A brief's "Built so far" paragraph is written in the planning commit that closes the merged ticket's inbox line, never ahead of the merge, and holds one paragraph (the manifest fails two). Use a detached worktree:

1. `git worktree add --detach ../ersa-plan origin/<branch>`, then `node scripts/role.mjs planning` inside it.
2. `git merge origin/main` if the branch is behind. Briefs, `docs/MANIFEST.md` and the ADR index merge with the union driver (`.gitattributes`), so two planning commits adding a Changes line or a requirement keep both; read the merged section once, then regenerate the manifest.
3. Update the briefs, delete the resolved inbox lines, run `node scripts/manifest.mjs --check`, commit, `git push origin HEAD:<branch>`.
4. Tell the implementing session to `git pull` before it pushes again. Remove the worktree when done.

## Merge

- The merge review adds a clean head to the merge queue through the gate (`scripts/merge-pr.mjs`) when CI is green. The queue builds and tests the merge before `main` moves and merges with a merge commit, so `Implements:` trailers stay (ADR 0023); a branch behind main needs no merge of main first. A head the queue removes (CI failed on the merge, or a conflict) needs a push, and CI and the review run again. A pull request that changes an owner-only path (workflows, hooks, instruction files, the review, the gate, the poller, or the manifest) is labeled `needs-owner`, and the owner merges it. A bot's pull request (a dependency bump) gets the label without a review, since taking a new version is the owner's call (ADR 0015). One labeled `hold` is reviewed and never enqueued; for a `hold` put on after the head was enqueued, the poller turns auto-merge off on its next tick, and its log says if GitHub refused. A push after the head was enqueued leaves auto-merge on, so the poller turns it off on its next tick; the new head is reviewed and enqueued again when clean.
- After a merge, `git pull` in the integration checkout and report to the owner in a few lines.
- When a batch's last ticket merges, cut one more: a retirement ticket for the surface the batch replaced (a control moved elsewhere, a list a tree superseded), found by reading the batch's briefs' "Built so far" against the interface. Surface no ticket retires is what the owner finds by hand.

## Train the harness

Merges are automatic, so the harness is trained in batches. Run a pass in a planning session when the owner asks. When you report a merge, offer one if 10 or more pull requests have merged since the last pass and no pass's pull request is open (`gh pr list --author @me --search "Harness: lessons from in:title"`). The last pass is the newest commit on `main` whose subject starts `Harness: lessons from`; `git log --first-parent --merges --oneline <that commit>..origin/main` lists the pull requests merged since; leave out the pass's own.

1. Run `node scripts/harness-lessons.mjs`: for each of those pull requests it sets what the merge review posted (the reviews by the owner's account that start `<!-- merge-review -->`; anyone can post a review on a public repository) against the **Review** section of the pull request's body, which lists what the implementing session's own review caught, and prints each blocking finding with whether that section names its file. It caches what it fetched under `.scratch/harness-lessons/`, so a second run costs no API calls. It names a pull request with no merge review or no **Review** section as not compared; say so in the commit. The script prints; which findings were misses is the planning session's judgment.
2. For each defect the merge review found that the author's review missed, and each defect found on `main` since the last pass, which both reviews missed, change the cheapest part of the harness that would have stopped it, in this order: a check in `scripts/` or the hook, a test convention, a reviewer agent's prompt or the `review-pr` skill, a brief requirement.
3. Take up the follow-ups each pull request's **Review** section lists: make each now, or file it as a `needs-triage` issue, so none is lost.
4. Prune at the same time: a rule nobody needs, a duplicated instruction, a stale note, and a reviewer-prompt clause whose findings changed no merge decision (ADR 0021).
5. Commit with a subject that starts `Harness: lessons from`, one body line per change naming the pull requests behind it, and title the pass's pull request with that subject. That commit is the record of the pass.
