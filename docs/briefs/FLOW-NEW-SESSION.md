# Start a new session

## Intent

A new session begins with the message, not with a form. The user chooses New session for a project and the transcript area becomes the new-session screen: the composer, focused, with the session controls beneath it saying where and how the session will run (host, project, whether it gets a worktree, backend, model, effort, permission mode; LAY-SHELL). Each control starts at what the user chose last time for that project, so the common case is to type and send. A model, effort or permission mode the user has already chosen on the screen stays when the project then changes, as long as its backend does: what the user just chose outranks what they chose last time. Each how chip reads the value the session will run with, as the chips of Claude Desktop's row do (`claude-desktop/permission-menu-2026-11-24.txt`), and never the word Default where the backend says what its default is: the backend's default model reads as the listed model it stands for, such as Opus, and an effort the user has not chosen reads as the level the backend says such a session runs with. A backend that doesn't say keeps its own name for its default model, since the name is the backend's, and its effort then reads Default. A value the user has not chosen is still left to the backend when the session starts, so the backend's own settings stand. The backend chip is always in the row, with one backend as with several, so the backend a session runs on is never left unsaid. The permission mode chip's list names and describes the modes as the backend's adapter gives them, which for Claude Code is as Claude Desktop's menu does. Once the session runs, its model chip names the choice the user made for as long as the backend reports the model that choice resolves to, and names the backend's report once it runs another. Nothing exists until the first message is sent: then Ersa makes the workspace, starts the backend in it, sends the message as the first turn, and the screen becomes the session's transcript with its tile in the rail.

The session controls lead with where the session runs, fixed once it starts: the host chip, the project chip and, for a project Ersa can make isolated workspaces for, a Worktree checkbox, as Claude Desktop's row has (`claude-desktop/new-session-row-2026-11-15.txt`). Checked, the session gets an isolated workspace of its own (a git worktree for a git project), made from the repository's default branch, not from whatever the project's folder has checked out (unless the repository has no other). Unchecked, the session runs in the project's own folder, the root workspace, for when isolation is not wanted: a quick question about the code. A project whose version control Ersa has no workspace adapter for has no checkbox, and its sessions run in its folder. Sessions in the root workspace share its files with each other and with the user.

The project chip on the new-session screen is the only place a project is added; the rail has no way to add one. Its list ends with Add project, which on the local host opens the system's folder dialog, then asks whether the user trusts the folder (ADR 0028), then chooses the new project. The trust question reads like the Claude Code CLI's own folder-trust prompt, which users already know, and has two answers: cancel, which it offers first, or trust. From the folder being picked until the question is answered and the project added, nothing is sent and no second folder dialog opens: a message sent then would start a session in the project chosen before (R42, R43). When the folder dialog can't be opened, or the folder can't be found or added, the screen says why above the composer, where the trust question opens, until the user chooses another project or host from the chips, picks a folder again or sends a message (R44): the reason is about the folder just picked, so it goes once the user has moved on, and it never stands where a send has something to say. A project is never added untrusted; the user withdraws trust later from the project heading's More menu (LAY-SHELL). Nobody types a folder path. With no project yet, the project chip offers to choose a folder, and sending opens the same dialog, keeping the message.

## Requirements

- **FLOW-NEW-SESSION-R01**: When the user chooses New session for a project, Ersa shall show the new-session screen in place of the transcript, with the composer focused and the session controls showing the host, project, workspace, backend, model, effort and permission mode the session will start with.
- **FLOW-NEW-SESSION-R02**: Ersa shall start the session controls at the values the user last started a session with for that project; with none, at a new isolated workspace (Worktree checked) for a git project and the root workspace otherwise, the first available backend on the project's host, that backend's default model and effort, and the permission mode in which the backend asks before every action outside its allow rules.
- **FLOW-NEW-SESSION-R03**: Ersa shall create no workspace and no session until the user sends the first message from the new-session screen; leaving the screen without sending shall leave nothing behind.
- **FLOW-NEW-SESSION-R04**: When the user sends the first message with a new workspace chosen, Ersa shall create an isolated workspace for the project, start a session in it with the chosen backend, model, effort and permission mode, and send the message as the session's first turn.
- **FLOW-NEW-SESSION-R05**: When the user sends the first message with the root workspace chosen, Ersa shall start the session in the project's root workspace, the project's own folder, with the chosen backend, model, effort and permission mode, and send the message as the session's first turn.
- **FLOW-NEW-SESSION-R06**: When the project's version control has no workspace adapter in Ersa, the session controls shall show no Worktree checkbox and the session shall start in the root workspace.
- **FLOW-NEW-SESSION-R07**: The session controls shall offer the backends detected on the project's host, and shall show a backend that is missing or failed detection with its status rather than hide it.
- **FLOW-NEW-SESSION-R08**: When the backend fails to start, Ersa shall show the failure on the new-session screen with the backend's own message, keep the user's message in the composer, and remove the session and any workspace it created for that session.
- ~~**FLOW-NEW-SESSION-R09**~~: retired 2026-11-05 (workspaces are not a level in the rail), replaced by R12 and R13.
- ~~**FLOW-NEW-SESSION-R10**~~: retired 2026-11-05 (a project is added from the project chip, by the folder dialog), replaced by R16 to R20.
- **FLOW-NEW-SESSION-R11**: When the project's host cannot list its backends, the session controls shall say that detection failed, with the reason, rather than that no backend is available.
- **FLOW-NEW-SESSION-R12**: When the session has started, Ersa shall make it the active session and show the session's values in the session controls.
- **FLOW-NEW-SESSION-R13**: When the session has started, Ersa shall show its tile in the rail where the rail's arrangement puts it (FLOW-ORGANIZE-SESSIONS).
- **FLOW-NEW-SESSION-R14**: The project chip shall list the projects on the chosen host, most recently used first (by its newest session), each with its name, its folder's path, its kind (Git or Folder) and, when it is not trusted, that it is not trusted, with the chosen project marked, and shall end the list with Add project.
- **FLOW-NEW-SESSION-R15**: When the user opens the session controls for no particular project (New session at the top of the rail, or no active session), Ersa shall choose the host's most recently used project.
- ~~**FLOW-NEW-SESSION-R16**~~: retired 2026-11-06 (the trust question says only what the CLI's prompt says), replaced by R27.
- **FLOW-NEW-SESSION-R17**: When the user cancels the folder dialog or the trust question, Ersa shall add no project and leave the session controls and the composer as they were.
- **FLOW-NEW-SESSION-R18**: When the folder the user picks is already a project on that host, Ersa shall find it before asking anything and choose that project without the trust question.
- **FLOW-NEW-SESSION-R19**: When the local host is chosen and has no projects, the project chip shall offer to choose a folder, and sending a message shall open the folder dialog as R27 does and keep the message in the composer; once the project is added it is chosen, and the message waits for the user to send it.
- **FLOW-NEW-SESSION-R20**: Ersa shall offer no field for typing a project's folder path.
- ~~**FLOW-NEW-SESSION-R21**~~: retired 2026-11-15 (the Worktree checkbox replaces the workspace chip, and nobody picks a base branch), replaced by R38.
- ~~**FLOW-NEW-SESSION-R22**~~: retired 2026-11-06 (the chip names no base branch before the branches are read, R28), replaced by R29.

- **FLOW-NEW-SESSION-R25**: The trust question shall offer two answers, Cancel first and then Trust, with keyboard focus on Cancel when it opens; Trust shall add the project as trusted, and Ersa shall offer no way to add a project that is not trusted.
- **FLOW-NEW-SESSION-R27**: When the user chooses Add project, or presses Ctrl+O on the new-session screen, with the local host chosen, Ersa shall open the system's folder dialog; once the user picks a folder that is not yet a project, Ersa shall ask the trust question (R24), and once they answer Trust, add the project as R25 says and choose it in the session controls.

- **FLOW-NEW-SESSION-R34**: A refused change's line shall be kept for its session, through a switch to another session and back, until the user sends or opens a chip in that session.

- **FLOW-NEW-SESSION-R38**: With Worktree checked, R04 shall create the isolated workspace naming no base, so that Core makes it from the repository's default branch, or, when the repository has none, from the checked-out commit (PROTO-CORE-API-R19), and Ersa shall read no branches for it.

A default choice with no `resolved` id, or one whose `resolved` id no other listed choice has, shall stay in the list and read by the backend's own label.
- **FLOW-NEW-SESSION-R47**: On the new-session screen while no effort is chosen, and under a session while `session.list` reports no effort for it, the effort chip shall read the level `backend.list` marks as the backend's default, where the model takes that level, and its list shall hold the levels alone, with that level marked; a session started with no effort chosen shall name none to the backend, and choosing a level, the marked one included, shall choose it. Where the backend marks no default effort, or the model takes efforts and not the marked one, the chip shall read Default, and on the new-session screen Default shall be the first row of its list, marked while no level is chosen.
- **FLOW-NEW-SESSION-R48**: While the host's backends are listed, the session controls shall show the backend chip, with one backend as with several: on the new-session screen naming the backend the session will start with, or saying that there is none when none can run (R07), and under a session naming that session's backend by its label.

## Verification

The replay server refuses every request that would create or change a session (PROTO-CORE-API, Conformance), so it cannot run R03 to R08, R12, R13 or the adding of a project in R27, R18 and R19. Those run against a real Core with a stand-in backend that can answer or fail to start; the Interface's own sequence is tested against a fake client, with the system's folder dialog replaced by a stand-in that answers with a folder or a cancel.

## Built so far

New session shows the new-session screen and creates nothing until the first message (R01 to R05, R08, R12), and a started session's tile sits under its project (R13). A project is added from the project chip through the system's folder dialog, after the trust question (R14 to R20, R24, R25, R27, R42 to R44). A Worktree checkbox chooses between a new isolated workspace, made from the default branch, and the project folder (R37 to R39). Values chosen on the screen survive a change of project (R32). Under a running session the session controls name its model by the user's choice (R33) and change its model, effort and permission mode (R30, R34, R35). A host whose backend listing fails says that detection failed (R11). Withdrawing a project's trust leaves a note beneath its heading until it is trusted again (R40, R41). The screen does not yet say while backends are being detected (R23). With no session chosen, the window shows the newest.

## Open questions

- What a session's row shows of its backend, model, effort and permission mode while its host's backends are being detected or can't be listed: R23 and R11 speak of the new-session screen, and R48 of a host whose backends are listed.
- Whether a session's effort is read from its own backend when it starts, so the chip reads that session's own before its first reply is recorded: until then R47 reads the host's default, which a project's settings can differ from (PROTO-CLAUDE-CODE-STREAM, Open questions).
- What the note after a withdrawal says once a second backend keeps a folder trust of its own. Today it names Claude Code.
- The mode control (a named preset, milestone M3) and where it sits among the session controls.
- Which session a reopened window shows when several were running.
- How the user picks a folder on a remote host, which the system's folder dialog cannot browse (FLOW-REMOTE-SESSION).
- What stands in the Worktree checkbox's place for other kinds of version control, and whether a worktree can start from a branch other than the default. The checkbox is git's; the owner expects other setups to get controls of their own (2026-11-15).
- What the trust question's security guide link opens, as the CLI's prompt has one. Ersa has no user guide yet, and the CLI's guide is one backend's, so the question has no link until one exists.
