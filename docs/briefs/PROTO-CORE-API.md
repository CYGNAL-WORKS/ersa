# Core request/response API

The protocol between the Interface (in the Shell) and the Core process: everything that is not an agent event. Requests from the Interface, responses from Core, and notifications from Core carrying agent events for subscribed sessions. The machine-readable form is `protocol/schema/core-api.schema.json` at the repository root, maintained by the implementing ticket; TypeScript types for the Interface are generated from it.

## Parties

One Core process per machine (the user's local machine, or a remote host reached through an SSH tunnel). One or more Interfaces attach to it. The replay server implements the same protocol over recorded fixtures.

## Transport and framing

A local stream socket: a named pipe on Windows (`\\.\pipe\ersa-core-<user SID>`, the SID because a user name comes from the environment), a Unix domain socket elsewhere (`$XDG_RUNTIME_DIR/ersa-core.sock` or equivalent). Only the current user may connect: the pipe's security descriptor grants the current user alone, and the socket lives in a directory only the user can enter. Before sending anything, a client verifies that the process serving the pipe or socket runs as the same user, and refuses to talk to it otherwise, so a squatter on the name never receives the user's requests. Lines are capped at 16 MiB; an over-long or non-UTF-8 line gets a protocol error and the connection closes. A connection that sends no `core.hello` within 10 seconds is closed. The endpoint is per user by default; `ersa-core serve` (and `replay`) also accept an explicit endpoint, so tests and a second Core never collide with the user's own. An explicit endpoint is a label (letters, digits, `-`, `_`) that Core appends to the user's endpoint name in the same private place, so it is exactly as private as the default; Core takes no raw pipe name or socket path, and no environment variable overrides the endpoint. Newline-delimited JSON-RPC 2.0: requests carry `id`, `method`, `params`; responses carry `id` and `result` or `error`; notifications carry `method` and `params` with no `id`. Either side may send notifications. Core writes nothing unsolicited except `session.event` for active subscriptions and, to every connection past `core.hello`, `session.tile`, `session.send_progress`, `host.status` and `core.notice`; a connection that cannot keep up is closed, except for `session.tile` and `session.send_progress`, which never close one (see Notifications).

## Handshake

The first request on a connection is `core.hello` with `{ client, client_version, api_versions: [..] }`. Core answers `{ core_version, api_version, event_projection_version, host: { id, name, platform }, capabilities: [..] }`. If no `api_version` overlaps, Core answers with an `invalid_state` error whose message and `detail` name the versions it supports, and closes.

## Methods

Names are `noun.verb`. Identifiers are strings Core issues. Listing methods return arrays of the full object; mutating methods return the affected object. Every time Core sends is RFC 3339 in UTC with millisecond precision. A limit in characters counts Unicode scalar values, which is not a JavaScript string's `length`.

### Core

- `core.hello`: see Handshake.
- `core.status`: `{ sessions_running, sessions_waiting, uptime_s, db_path }`.
- `core.shutdown`: stops all sessions cleanly and exits. Interface disconnect alone never stops sessions (ADR 0011).

### Hosts

- `host.list`: the local host and configured remote hosts: `{ id, name, kind (local | ssh), status (connected | disconnected | unknown), backends: [{ name, version (optional, present when available), status (available | missing | error) }] }`.
- `host.add`, `host.remove`, `host.probe` (re-detect backends and VCS tools): remote hosts are milestone M4; the methods are reserved now so the Interface shape is stable.

### Projects

- `project.list`, `project.add { host_id, path, trusted }`, `project.set_trust { id, trusted }`, `project.remove { id }`: `{ id, host_id, path, name, vcs (git | perforce | none), trusted }`. `project.find { host_id, path }`: the project on that host whose folder is `path`, compared as `project.add` compares folders, or null. The Interface asks it before the trust question, so a folder that is already a project is chosen without one (FLOW-NEW-SESSION-R18). `project.add` for a folder that is already a project on that host is refused with `invalid_state`, and the error's `detail` is that project's id. `trusted` is true for a project the user adds, since adding one is trusting it (FLOW-NEW-SESSION-R25), and only a trusted project's own configuration loads in its sessions (ADR 0028); left out, it is false. `project.add` and `project.find` refuse a relative path with `invalid_params`. `project.add` also refuses a drive or share root with `invalid_params`, answers `not_found` when no folder is at the path, and `permission` when the folder can't be opened; `project.find` answers null for a folder it can't resolve. Projects are listed in the order they were added. `project.remove` is refused with `invalid_state` while the project has an isolated workspace or a session in its root workspace; it never cascades.

### Workspaces

- `workspace.list { project_id }`, `workspace.create { project_id, name (optional), base (optional) }`, `workspace.remove { id, force (optional) }` (refused with `invalid_state` while the workspace has sessions; it never cascades): `{ id, project_id, kind (root | isolated), path, vcs_ref, state (ready | creating | removing | error) }`. A session is created in, or forked from, only a `ready` workspace; any other state answers `invalid_state`. Every project has one root workspace, its own folder, which exists from `project.add` and is listed first, the others following in the order they were made; its `vcs_ref` is empty, since that checkout is the user's to change. `workspace.create` makes an isolated workspace (a git worktree for a git project) and is refused with `invalid_state` for a project whose version control has no workspace adapter. `name` is the new branch's name, `ersa/<workspace id>` when left out; Core refuses an empty one, or one that starts with `-`, with `invalid_params`. `workspace.remove` refuses the root workspace, and a workspace still `creating` or already `removing`, with `invalid_state`, and otherwise returns the workspace as it was claimed for removal, with `state: removing`. `base` names what an isolated workspace starts from: a branch from `branch.list`, or any other revision git can resolve (a tag, a commit, `main~1`); Core refuses one git can't resolve, and one that starts with `-`, with `invalid_params`, and passes it to git as a revision, never as an option. Resolving it has a 10-second limit, past which Core answers `vcs_error`. Without `base`, Core starts from the repository's default branch, as `branch.list` marks it, or from the checked-out commit when none is marked.
- `branch.list { project_id }`: the project's local branches, for choosing a new workspace's base branch: `[{ name, default }]`, sorted by name. At most one is `default`: the local branch `origin/HEAD` points at, else `main`, else `master`, else the branch the project's folder has checked out; never what is checked out while one of the others exists, and none on a detached checkout with none of the others, when `workspace.create` without `base` starts from the checked-out commit. Core gives its git call a 10-second limit and answers `vcs_error` when it runs out. Refused with `invalid_state` for a project whose version control has no workspace adapter, and with `vcs_error` and git's message when git fails.
- `workspace.changes { id }`: what deleting an isolated workspace would lose, for the delete question (FLOW-ARCHIVE-DELETE-SESSION): `{ uncommitted, ignored, unshared, stranded, sessions, unrecorded, token }`. `uncommitted` counts files with changes not committed, untracked files included; `ignored` counts the ignored entries the version control reports, a wholly ignored folder as one, which deleting the folder deletes too; `unshared` counts commits reachable from the workspace's checkout, its branch (`vcs_ref`) or its own reflog that no other local branch or remote-tracking branch holds, so commits made on a detached checkout count; `stranded` counts those of them the workspace's branch does not hold, which deleting the folder loses, since only the branch is kept; `sessions` counts the sessions using the workspace, leaving out any marked deleting. `token` is an opaque value that changes whenever the uncommitted files or their content, the unshared commits, the set of ignored entries (not their content) or the sessions it counts change. It answers for a workspace whose deletion has begun, counting what is left, even when its folder is partly or wholly gone. A tracked file missing from the folder is uncommitted only when the index holds something for it the commit does not (staged, then deleted): one deleted with nothing staged, or its deletion staged, loses nothing the commit does not keep, so a half-removed folder's missing files do not count, though the deletion still changes `token`. When git no longer has a record of the workspace (on Windows a failed removal can delete git's record and leave files behind), git can't say which files were committed, so every file left that the ignore rules do not ignore counts as uncommitted, `unshared` counts only the commits the workspace's branch holds that no other branch does, and `stranded` is 0, since the checkout and its reflog went with the record; commits made on a detached checkout are then beyond counting, the one loss Core cannot see, so `unrecorded` is true and the delete question says so. A submodule or nested repository counts as one uncommitted entry when it has uncommitted changes or commits that none of its own branches' remotes hold, since deleting the folder deletes them, and its HEAD and status go into `token`. With git's record gone, `token` follows the files left and the branch's commits, never the root checkout's. Core gives the request's git calls and file reads 60 seconds together and answers `vcs_error` past it, stopping the work, not only the wait; the request runs apart from the connection's other requests, which never wait for it. Refused with `invalid_state` for a root workspace, whose files are never deleted.

### Sessions

- `session.list`: `{ id, workspace_id, host_id, backend, model, effort, permission_mode, mode, title, state, created_at, last_event_seq (absent before the first event), sending (absent unless a send is under way: its phase, as `session.send_progress` names it), pinned, section_id (absent when in no section), archived, unseen, deleting (running | failed; absent unless the session is marked deleting), last_activity_at (absent while no last activity is known), tile: { state, context_tokens, context_window, cost_usd_total, pending: [{ kind (permission | question), request_id }], waiting (how many messages the backend holds behind the running turn; absent when none, or when the session is not live) } }`. The `tile` object is what the rail renders; Core keeps it current from events, and its `waiting` from what the backend reports holding. A session's `title` is its backend's: the title the backend's own tools list for it, which Ersa never stores; for a live session whose record holds no title yet, the latest title its backend announced on the live stream, held in memory only, like any detail only the live stream carries. Its `created_at` is the time of the first entry in its session record, else the time of the app log's first fact for it. Its `mode` is Ersa's. A session's `model`, `effort` and `permission_mode` are its backend's newest report of them (PROTO-CORE-API-R71): what a live session's stream has reported of its model and permission mode, otherwise the record's value from a turn that began after Core's last request for it, or from any turn for a session Core made no request for, such as one started elsewhere, else that request. `pinned`, `section_id`, `archived` and `unseen` are the user's arrangement, which Core stores (ADR 0033); `last_activity_at` is, for a session that is not live, the time of the latest conversation entry in its record, and for a live session the `ts` of its latest `turn.completed` since it went live, whatever the outcome, else what its record gave when it went live, held in memory only (PROTO-CORE-API-R75). Sessions are listed oldest first by `created_at`, then by `id`, and `title` is absent while no title is known. A session Core lists for the first time starts with none of them set. A deleted session is never listed again, since its record is gone; one marked deleting carries `deleting`: `running` while Core works on it, `failed` after a step failed.
- `session.create { workspace_id, backend, model (optional), effort (optional), permission_mode (optional), mode (optional) }`: creates and starts; it takes no title, since the title is the backend's. `model`, `effort` and `permission_mode` are ids from `backend.list`; Core refuses any other id with `invalid_params`, and a `backend` it has no adapter for with `backend_missing`. A `model` or `effort` left out is left to the backend, and Core keeps what was named, with the time, as R71 says: until its backend reports its own, `session.list` reports the named values and leaves the others absent, which means the backend's own default (a replayed session, and a session created before these fields existed, report none). The permission mode is the exception: the backend must always be told one (PROTO-CLAUDE-CODE-STREAM, Invocation), so a `permission_mode` left out becomes the backend's default mode, stored and reported as the mode the session started with. The `default` marks in `backend.list` say what the backend chooses on its own, for the session controls to show, not what a given session ran with; a backend that marks no default effort has none, and the session controls show effort as unset. `mode` is stored and shown; it takes effect from milestone M3, when modes exist.
- `session.start { id }`, `session.stop { id }`, `session.resume { id }`, `session.remove { id }`. Restarting a stopped session is `session.resume` (milestone M1); until then `session.start` on a stopped session answers `invalid_state` naming M1. `session.start` on a live session answers `invalid_state`, and `session.stop` on a session that is not running does nothing and succeeds. `session.resume` on an archived session clears `archived` when Core accepts the resume, before it starts the backend; a refused resume, including the `invalid_state` naming M1 until then, leaves the session archived, and a backend that fails to start after that leaves it unarchived and stopped, as Unarchive does. `session.remove` is refused with `invalid_state` while the session is live. A session stops being live once its `session.ended` is sent, so a client that has seen `session.ended` can always remove it: when Core is still letting go of that session, `session.remove` waits for it, for a bounded time, and answers `internal` with the session left as it was if the wait runs out (PROTO-CORE-API-R41). `session.remove` removes the session alone, leaving its workspace, and is how the Interface cleans up a session that failed to start.
- `session.delete { id, token (for an isolated workspace) }`: the user's Delete (FLOW-ARCHIVE-DELETE-SESSION), in this order. (1) Core claims the workspace for this delete, in memory only, leaving the workspace's stored state unchanged until step 4; while the claim is held, `session.resume`, `session.send`, `session.fork`, `session.set_archived` and `session.arrange` of this session, and any other `session.delete`, `session.create`, `session.fork` or `session.remove` touching that workspace, answer `invalid_state` with `detail` the string `busy`, and a restart drops the claim. (2) Core stops the session; when the stop fails or times out, Core releases the claim and answers with the stop's error. Only then does Core ask the backend's live-session registry: no transport lets Core tell its own process apart there, and a stopped process has left it. When it shows any process with the session open, or cannot say, Core releases the claim and answers `invalid_state` naming the process or the reason, leaving the session stopped. Either way it has deleted and marked nothing. (3) For an isolated workspace Core computes `workspace.changes`; when it differs from `token`, Core releases the claim and answers `invalid_state` with `detail` the new `workspace.changes` object as JSON text, since `detail` is a string, leaving the session stopped and otherwise unchanged; when it fails (`vcs_error`, its time limit among them), Core releases the claim and answers with that error. (4) Core records the session as deleting with `deleting: running`, and records whether its files go: they go when `workspace.changes` counted no session but this one. When they go, the same transaction sets the workspace's state to `error`, so no session starts in a workspace whose folder may be going or gone, even after a crash part way through step 5. For a session already marked deleting, the record is kept and never widened: files that were to stay still stay. (5) When the record says the files go, Core deletes the folder and, for git, the branch named by `vcs_ref`, unless another worktree has it checked out or the branch itself holds unshared commits (those `unshared` counts and `stranded` does not), which keep it. (6) Core deletes the session's record from its backend through the adapter (for Claude Code, PROTO-CLAUDE-CODE-STREAM, Deleting). (7) In one transaction it removes the session, and the workspace when its folder is gone and no other session refers to it. A session marked deleting no longer uses its workspace: it is left out wherever this method or `workspace.changes` asks which sessions use one, so another session's delete can take the folder while its row still refers to the workspace, which then stays until that session's own delete removes it, deleting no files. A root workspace is never touched and needs no token. A call without `token` for an isolated workspace answers `invalid_params` before any other refusal but an unknown session's `not_found`. When step 6 finds the session newly open elsewhere, Core marks the session `deleting: failed`, releases the claim, and answers `invalid_state` naming the process. When step 5 or 6 fails otherwise, Core marks the session `deleting: failed`, releases the claim, and answers `vcs_error` (or `internal`) with the reason. Trying again is a new `session.delete` with a token from a fresh `workspace.changes`, so the user is shown what is left before anything more goes. At startup Core marks every `running` delete `failed` and deletes nothing until the user tries again. A session marked deleting is refused `session.resume`, `session.send`, `session.fork`, `session.set_archived`, `session.arrange` and `session.remove`. Refused with `invalid_state`, once step 1's claim is held and before step 2, releasing the claim, while the session is starting, a message is being sent to it, or a turn is running in it, a turn waiting on the user included. Returns `{ id, workspace_deleted, branch_kept }`: `workspace_deleted` is true when this delete deleted the workspace's folder, whether or not the workspace's row outlives it. It does not go through `workspace.remove`'s refusal.
- `session.arrange { id, pinned (optional), section_id (optional; `null` for no section), unseen (optional) }`: changes the fields given and leaves the others (FLOW-ORGANIZE-SESSIONS); `not_found` for a section that does not exist. `session.set_archived { id, archived }`: archiving stops a live session first, as `session.stop` does, and is refused with `invalid_state` while the session is starting, a message is being sent to it, or a turn is running in it, a turn waiting on the user included. Each returns the session as `session.list` lists it.
- `session.interrupt { id }`: stops the turn the agent is working on; the turn ends with `turn.completed` and outcome `interrupted` (PROTO-AGENT-EVENTS). A message not yet handed to the backend is canceled instead (Turns and attachments). A message the backend holds behind the turn runs next. With neither a turn nor a message, it does nothing and succeeds.
- `session.fork { id }`: starts a fork (FLOW-FORK-SESSION). For an original in an isolated workspace, Core makes a new isolated workspace as `workspace.create` makes one, on a new branch starting from the commit the original's workspace has checked out, leaving uncommitted changes behind; for an original in a root workspace, the fork runs in that workspace. It has the original's backend, its model, effort and permission mode as `session.list` reports them when forked, and its section, not pinned and not archived. Core returns the new session as `session.list` lists it. Core makes the workspace only after every refusal of this method; one it can't make answers as `workspace.create` does and leaves no fork. A fork that later fails to start keeps that workspace until the fork is deleted. Until the fork's backend is ready, `session.delete` of the original answers `invalid_state`. Core has a titled original's fork named in its backend when it starts, with the original's title, shortened so the whole fits `session.set_title`'s limit, followed by ` (fork)`. A fork's `title` and `created_at` are the backend's, as any session's are, and Ersa stores neither and holds no title of its own: a fork's title is what the backend has announced or its record gives. After a naming the backend refuses, the fork's record gives the title it copied, and a fork never sent a message has no title after a restart. A fork's link to its original's record is kept only until the fork has a record of its own (FLOW-FORK-SESSION-R09). The first time in a fork's record is the original's, so once it has a record its `created_at` is the original's date; until then it reads as any session's with no record does. Core decides from the session record, not from turns it saw: the fork is refused with `invalid_state`, each case with its own message, when the record's conversation does not end with a finished reply (none yet, or a last turn that was interrupted or is still being written), while a turn is running in the original, while another fork of it is starting, when the backend's live-session registry shows more processes with the session open than the one Core runs for it, if any, since Core can't tell its own process apart there (an answer the registry cannot give does not refuse), before the backend has named the session, and when the backend cannot fork.
- `session.send { id, text, attachments (optional) }`: sends a user message with its attachments; what it answers, and when, is under Turns and attachments, below. `text` may be empty when there are attachments. To an archived session, Core answers `invalid_state`. To a session whose backend is still starting, Core sends once it has started. To a session being forked, Core answers `invalid_state` until the fork's backend is ready, since a turn started before the backend has read the record would be copied part way. To one whose backend failed to start, Core answers `invalid_state` with "the backend could not be started:" and the adapter's reason, including the backend's own error output, so the new-session screen can show it (FLOW-NEW-SESSION-R08).
- `attachment.inspect { path, workspace_id or host_id }`: what the composer shows for a file, image or folder the user added by path, read on the workspace's host, or on `host_id` for a new workspace not yet made: `{ path, name, kind (file | image | folder), size_bytes (file and image), lines (optional: a text file's line count), media_type (image), target (optional: where a link points), copied }`. It takes exactly one of `workspace_id` and `host_id`; both or neither is `invalid_params`. `copied` is true for a file or folder whose target, resolved as a send resolves it (links, junctions, `..`), is outside the workspace, and false for an image, which goes inline, and for a path inside the workspace; given a host, nothing is inside the new workspace yet. It measures nothing: a copy's size and number of entries are the send's to refuse (`attachment_refused`). The Interface shows the note that an attachment will be copied from `copied` alone. A folder that holds the workspace can never be sent, so inspect refuses it with `attachment_refused` and the reason. A `workspace_id` or `host_id` that names nothing is `not_found`. `copied` is a preview: a path that changes before the message is sent is judged again by the send, whose judgment is the one that holds. `not_found` when nothing is at the path, and `invalid_params` for anything but a regular file or a folder (a pipe, a device), or when its 30-second limit is reached. An image is a file whose first bytes are one of the image types the host's backends take; Core reads those bytes, not the name, to tell. Core counts lines only in a text file of at most 10 MB, and returns no content.
- `session.decide_permission { id, request_id, behavior (allow | deny), message (optional), updated_input (optional), apply_suggestions (optional array of indices) }`. A session that is not live answers `invalid_state`, whatever the `request_id`. On a live session, a `request_id` that names no pending request of this kind, one already answered included, is `not_found`, and with `behavior: allow` an index no suggestion has is `invalid_state`.
- `session.answer_question { id, request_id, answers, declined (optional) }`: `answers` in `question.answered`'s shape (`PROTO-AGENT-EVENTS`); `answers` is always present, and `declined: true` with `answers: []` says the user chose not to answer; `declined` with answers is `invalid_params`. The session and `request_id` are judged as `session.decide_permission` judges them. Core refuses with `invalid_state` answers that miss a question or repeat one, answer a question it did not ask, name an option the question did not offer or choose one twice, give a list to a single-choice question, or give different answers to questions the backend can't tell apart (for Claude Code, questions with the same text: PROTO-CLAUDE-CODE-STREAM, Questions).
- `session.set_title { id, title }`: renames the session in its backend, so the new title shows in the backend's own tools too (for Claude Code, `PROTO-CLAUDE-CODE-STREAM`, Session record). Ersa keeps no title of its own: the new title is the name the backend took, which may differ from the one asked for (Claude Code may add a suffix that makes it unique). Core applies the title rules its backend's adapter states (PROTO-CORE-API-R70): it trims the title and takes each run of spacing as one space, and for a backend whose titles may span lines does so line by line, where a line break is LF or CRLF and any other break counts as spacing, dropping blank lines at either end, keeping those between, and counting each kept line break as one character toward the limit; it refuses with `invalid_params` a title that is then blank, longer than the backend's limit, or holding any other control character; every session can be renamed, a starting one included, through the backend's own naming (for Claude Code, the id of a new session or a fork is known from its start and the CLI takes a name before the first message: PROTO-CLAUDE-CODE-STREAM-R35, R36, R38). It answers `invalid_state` for a session whose record is gone or one that ended before its backend recorded it. The title is the backend's, so its rules are too: Claude Code's titles are one line of at most 200 characters.
- `session.set_mode { id, mode }` (takes effect on next start).
- `session.set_model { id, model }`, `session.set_effort { id, effort }` and `session.set_permission_mode { id, permission_mode }`: change a live session's model or effort through its backend from its next turn, or its permission mode at once; Core keeps the new value with the time, as R71 says, so a relaunch before a turn has run with it still passes it. Each value is an id from `backend.list`, any other being `invalid_params`. A session that is not live answers `invalid_state`. Each returns the session as `session.list` lists it.
- `session.subscribe { id, from_seq }`: Core sends every event with `seq >= from_seq` as `session.event` notifications, then continues live. Returns `{ view, last_seq, first_seq }`; `last_seq` is absent when the view has no events yet. A view holds a bounded amount of events (64 MiB); once it has let go of its earliest ones, `first_seq` is the first event it still holds, a subscription from before it starts there, and the Interface says that earlier events are no longer shown. `first_seq` is absent while the view holds every event from 0. A second `session.subscribe` to one session on one connection replaces the first. `view` identifies the projection Core is serving (when Core rebuilds one: `PROTO-AGENT-EVENTS`, Opening a session), and changes whenever Core rebuilds it. Sequence numbers count within a view, so a client holding events from a different view discards them and subscribes again from 0, or from `first_seq`.
- `session.unsubscribe { id }`.
- `session.remove` also removes the session's scratch folder (Turns and attachments).
- `session.raw_log { id, from, to }`: the session's raw log for the developer pane, the lines exchanged with its backend since Core opened it (held in memory, never stored): `[{ index, ts, dir (backend | host), line }]`, at most 1000 and at most 8 MiB of line text per call, one line always coming back however long; the client pages on from the last index plus one. Core's lifecycle facts are in the app log, not here.

### Sections

- `section.list`, `section.create { name }`, `section.rename { id, name }`, `section.remove { id }`: `{ id, name, created_at }`, listed in the order they were made. Core trims a name and takes each run of spacing as one space, as `session.set_title` does, and refuses with `invalid_params` one that is then blank, longer than 200 characters, or holding another control character. `section.create` with exactly another section's name returns that section and makes none, and `section.rename` to exactly another's name is refused with `invalid_params`. Names are compared character for character, so names that differ only in case are different sections (`claude-desktop/sections-2026-11-09.txt`). `section.remove` puts its sessions in no section.

### Turns and attachments

An attachment is a file, an image or a folder that goes with a message (FLOW-SEND-MESSAGE). `session.send` takes them as `attachments`, in the order the user added them:

- `{ kind: "image", path }`: an image file on the session's host, which Core reads.
- `{ kind: "image", media_type, data }`: an image the user pasted, as base64 `data` with its `media_type`.
- `{ kind: "file", path }` and `{ kind: "folder", path }`: a file or folder on the session's host, by absolute path.

Core checks every attachment before it sends anything, and refuses the whole message with an application error of `kind: attachment_refused` whose `data.index` is the place in `attachments` of the first one it can't send, and whose message says why:

- a path where nothing is, or whose name holds a control character;
- an image whose type or size the session's backend does not take (the adapter states its limits), or inline images that together exceed 10 MB, which leaves room under the line cap for the words (a request past the cap is still refused as a protocol error);
- a folder that holds the session's workspace;
- a copy of more than 100 MB or 10,000 entries, checked before copying and again while copying, so a file that grows meanwhile still stops the copy;
- a time limit reached (below), such as a read from a network drive that no longer answers.

An attachment that is a link is judged by its target and keeps its own name. An image goes to the backend inline, as an image the agent sees. A file or folder goes as its path relative to the session's workspace when its target is inside it. One outside it is copied first into the session's scratch folder, `.ersa/attachments/<session id>/<n>/` at the workspace's root, where `<n>` numbers the message's copies in order, the first one more than the highest number already in the session's scratch folder, so it is never reused, across restarts too, keeping its name, and goes as that copy's path. Each session has its own scratch folder, made by its own first copy, and no other session reads or empties it, so sessions that share a root workspace never touch each other's copies. A copied folder's links are left out, never followed. Core refuses the message when `.ersa`, `.ersa/.gitignore`, or any folder on the way to a copy is a link or otherwise not a real file or folder inside the workspace, and writes a `.gitignore` holding `*` into `.ersa/` whenever it has none, so version control ignores the folder. A copy is made aside, in the session's own `.partial/`, and moved into place only when whole; when any copy fails (a file gone or locked, the disk full, a time limit reached), Core removes what it copied for that message, including copies already moved into place, and refuses it with the reason, and the session's next send empties its `.partial/` first, so a crash leaves nothing behind for long. A session's copies stay while the session exists, and `session.remove` removes its scratch folder with it. Emptying and removing never follow a link: a link found there is removed itself, never what it points at.

Core takes the Interface's word that each path is one the user named (FLOW-SEND-MESSAGE-R13); it refuses nothing by where a path came from.

**Sending.** One message is sent at a time per session. A message sent while a turn runs is handed over at once; the backend holds it and runs it when the turn ends (PROTO-CLAUDE-CODE-STREAM-R43), and Ersa keeps no queue of its own: the tile's `waiting` is how many messages the backend reports holding (PROTO-CORE-API-R81). A second `session.send` from the same connection waits for the first one's answer, so one connection's messages keep their order; no other request waits behind a send. A `session.send` from another connection meanwhile is refused with `invalid_state`. A send passes through checking, copying, waiting for a starting backend, and handing the message to the backend; through all of them Core reports where it is as `session.send_progress` notifications (below), and `session.list` reports the session's `sending` phase while a send is under way, so an Interface that reconnects mid-send knows of it. Waiting for a starting backend is limited to 2 minutes and handing the message over to 30 seconds; past the first the message was not sent, past the second Core answers `delivery_unknown`, and either way the session can send again. All the file system work for one message, and each `attachment.inspect`, runs as one task Core can cancel, with a time limit of its own (5 minutes for a message, 30 seconds for an inspect; the Interface waits longer than each); when the limit is reached or the send is canceled, Core answers at once, and the work stops at its next step and then removes what it copied. A single file system call already under way, such as a read from a network drive that stopped answering, keeps its thread and the message's copies until it returns, so Core bounds what such calls can hold: the session's next send with attachments waits at most 30 seconds for a copy still stuck and is then refused with `invalid_state`, and at most 8 `attachment.inspect` reads run at once across Core, a further one being refused with `invalid_params` until one returns. Checking and copying never hold up `session.interrupt` or an answer to a permission request or question on the same session. `session.send` answers only when its message has been handed over or will not be:

- `{ turn }`: the backend has the message. `turn` is absent when Core has not projected the message yet; the `user.message` event follows.
- An error: the message was not sent, and nothing it copied remains once its work has stopped.
- An error with `kind: delivery_unknown`: Core handed the message over but can't tell whether the backend took it (the backend stopped mid-handover, say). The transcript shows it if it arrived.

`session.interrupt` before the message is handed over (while checking, copying, or waiting for the backend to start) cancels the send, which answers `invalid_state` saying the message was stopped. How the adapter puts the paths and images into the backend's message is the adapter's (for Claude Code, PROTO-CLAUDE-CODE-STREAM, User message). The `user.message` event for the turn carries the attachments as sent (PROTO-AGENT-EVENTS).

### Backends and modes

- `backend.list { host_id }`: `{ name, label, version (optional, present when available), status (available | missing | error), tested { min, max }, models: [{ id, label, default, resolved (optional), efforts (ids; absent when the model takes none) }], efforts: [{ id, label, default }], permission_modes: [{ id, label, default }] }`. A model's fields are the backend's own report, read from the backend on the host (PROTO-CORE-API-R72); `resolved` is the model id a session of that choice reports, so the session controls can name it, a backend missing from the host is `missing`, and one present that can't give its report is `error`, either with no models. The efforts' labels and the permission modes, for which a backend reports no list, are the adapter's knowledge of its tested versions. `label` is what the Interface shows (the backend's own, such as "Claude Code") and `default` marks what the backend chooses on its own, which for a permission mode is also what a session given none starts with (PROTO-CORE-API-R71).
- `mode.list`: `{ name, description }`; modes as presets are milestone M3; the method is reserved.

### Settings

- `settings.get`, `settings.set { patch }`: user settings as a JSON object, patch-merged (RFC 7386). `settings.get` returns only what the user has set; defaults are Core's and are not echoed. A dot in a key's name below is a nested object: `rail.group_by` is `{ "rail": { "group_by": … } }`. Core stores the `rail.*` values without checking them. Known keys so far: `workspaces.root` (where workspaces are created; an absolute path, anything else being refused; default `worktrees` under Core's data directory); `new_session.last_used.<project id>` (`{ host_id, project_id, workspace, backend, model, effort, permission_mode }`, the values that project last started a session with, which the Interface writes after a start and reads to fill the session controls, FLOW-NEW-SESSION-R02; a value left out is sent as null, so the merge clears it); the rail's arrangement (FLOW-ORGANIZE-SESSIONS): `rail.group_by` (`project`, `section`, `date` or `none`; default `project`), `rail.sort_by` (`created`, `last_activity` or `name`; default `created`), `rail.show` (`active`, `archived` or `all`; default `active`), and `rail.collapsed.<group_by>` (the keys of the groups collapsed in that grouping: `pinned`, a project or section id, `no_section`, or `today`, `yesterday`, `previous_7_days`, `older`; default none). Reset to defaults sends each `rail.*` key as null.

### Workbench (milestone M2, reserved)

- `fs.list { workspace_id, path }`, `fs.read { workspace_id, path, range (optional) }`, `fs.diff { workspace_id, base (optional) }`.
- `terminal.open { workspace_id }`, `terminal.input`, `terminal.resize`, `terminal.close`, with a `terminal.output` notification.

## Notifications (Core to Interface)

- `session.event { session_id, event }`: one `PROTO-AGENT-EVENTS` envelope.
- `session.send_progress { session_id, phase (checking | copying | starting | handing_over), copied_bytes (copying), total_bytes (copying) }`: where a send is, sent when its phase changes and at least every 5 seconds until it is answered, at most once a second. Coalesced like `session.tile`: a busy connection gets the newest per session, and it never closes a connection. The Interface waits for its send's answer for as long as these keep arriving.
- `session.tile { session_id, tile, last_activity_at (absent while no last activity is known) }`: the tile object or the session's last activity changed (so the rail updates and sorts without subscribing to every session's events). It carries `last_activity_at` as `session.list` would list it when sent, and Core sends one when a turn ends, even if the tile is otherwise unchanged. A tile is the session's whole state, so tiles are coalesced: Core may project several backend lines at once and publish one tile for them, and a connection that is busy gets only the newest tile per session when it is ready, never a backlog. A client therefore sees some of the tiles a session passes through, in order, always ending on the current one; for tiles, PROTO-CORE-API-R09's same notifications means that.
- `host.status { host_id, status }`.
- `core.notice { level (info | warning | error), message }`: for things the user should see that belong to no session.

## Errors

JSON-RPC error objects with `code` (standard JSON-RPC codes for protocol-level failures, including `-32602` for invalid params; `-32000` for application errors), `message`, and, on application errors only, `data: { kind, detail (optional), index (optional), reason (optional) }` where `kind` is one of `not_found`, `invalid_state`, `backend_missing`, `backend_not_logged_in`, `vcs_error`, `transport_error`, `permission`, `internal`, `attachment_refused` (with `index`, the refused attachment's place, on a send), `delivery_unknown`.

A method naming a session, project, workspace, section, host or pending request that does not exist answers `not_found`, unless this document gives that method another answer first: a reserved method, `session.resume` until M1, a replay's refusal, a pending request on a session that is not live. `session.unsubscribe` of a session not subscribed succeeds.

`reason` names a refusal the user meets, so the Interface can say it in the string catalog's words (`docs/design/CONTENT.md`). Core's `message` stays for the log and for what has no `reason`. The reasons, each on `invalid_state`:

- `session_busy`: the session is starting, a message is being sent to it, or a turn is running in it (`session.set_archived`, `session.delete`, `session.fork`).
- `session_deleting`: the session is marked deleting.
- `session_archived`: a message to an archived session.
- `session_not_running`: the session has no live backend.
- `send_in_progress`: another connection is sending to the session.
- `send_stopped`: `session.interrupt` stopped the message before it was sent.
- `resume_not_built`: `session.resume` or `session.start` until milestone M1.
- `backend_unnamed`: the backend has not reported the session's id yet.
- `record_gone`: the backend has no record of the session.
- `open_elsewhere`: another process has the session open, named in `detail`.
- `open_unknown`: Core can't tell whether another process has the session open.
- `no_finished_reply`: the record's conversation does not end with a finished reply.
- `backend_cannot_fork`: the backend, or the version installed, can't fork.

## Versioning

`api_version` negotiated in the handshake; additive changes (new methods, new optional fields) keep the version; removals or meaning changes bump it. Reserved methods answer `invalid_state` naming their milestone until it arrives (PROTO-CORE-API-R10).

## Conformance

A conforming Core passes a request/response test suite driven over the socket, and the replay server passes the same suite with fixtures substituted for live backends. Generated TypeScript types compile against the schema.

The replay server answers read-only requests exactly as Core does. It never changes anything outside its own data: every request that would change a session, a project, a workspace or a setting answers `invalid_state` saying the session is a replay, so a replay cannot create worktrees in the user's repositories or alter their settings. A replayed session stays open and idle after its last recorded line until `core.shutdown`. Pacing defaults to the recorded timing; an instant pace is for tests. The replay server never serves the user's own endpoint: with no explicit endpoint it serves the label `replay`, so an Interface reaches a replay only when told to, and a replay never stands in for, or blocks, the user's Core. It applies Core's own limits to the recording, line size included, and a recording it cannot read faithfully is refused at start with the reason, never played with a default in its place.

A replay capture is what the replay server sent for one fixture, kept so the Interface's tests can replay it without running Core. It is a JSON object: `sessions` (`session.list` on attach), `sessions_after` (`session.list` once the replay has played out), `notifications` (every notification, in the order it arrived), and `ersa_commit` (the Ersa commit the capture was written from, ending `-dirty` when the tree had uncommitted changes outside the captures). A capture is checked against a fresh run of the replay server, which fails when the capture is stale. The check ignores `ersa_commit`, which says where a capture came from, not what it holds. Rewriting the captures builds Core first, so a capture never records a stale build.

- Whether `attachment.inspect` becomes part of the workbench's `fs` methods when they arrive (M2).
- Whether to allow more than one Interface attached at once (useful for a second window), and if so whether notifications fan out to all.
- Whether Core notifies an Interface when a project or session is created, and pushes `core.status` when its counts change; until then the window rereads `session.list` on a `session.tile` for an unknown session and reads the counts at attach.
- Whether the window still reads `core.status` at attach. Nothing in the window shows its counts now that the rail's foot is silent while all is well.
