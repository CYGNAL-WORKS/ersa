# Clean up what Ersa leaves behind

## Outcome

The folders and branches Ersa made and no longer needs don't pile up. What holds no unsaved work goes on its own: an archived session's folder is put away, and what a failed start, a failed fork or a crash left is removed. Everything else waits on one list, and nothing on it is removed until the user approves, knowing what each removal loses (ADR 0038).

Archive, Clean up and their settings do what Claude Desktop's do (`claude-desktop/cleanup-2026-11-20.txt`), with one difference that may be Ersa's own: Archive inactive sessions stops no session (owner, 2026-11-26), so a session whose backend is still running is archived only after Ersa next starts, where Claude Desktop's words, "Running sessions are never archived", leave open whether it archives an idle one sooner. The sweep, the leftovers and the branches on the list are Ersa's own: nothing read of Claude Desktop says what it does with them.

## Trigger

The user archives a session; Ersa starts, or an hour passes; or the user opens Storage on the settings page (`LAY-SHELL`).

## Steps

1. **Archiving frees the folder.** After a session is archived (FLOW-ARCHIVE-DELETE-SESSION), Ersa puts its isolated workspace away: the folder is removed and the branch stays. A folder that holds unsaved work stays as it is, and so does one that holds a repository of its own, a submodule's or a nested one, which Ersa counts as unsaved work. Nothing is shown; the session reads as any archived one.
2. **Resuming brings it back.** When the user resumes the session, or unarchives it and writes to it, Ersa puts the folder back where it was, checked out as it was, and then resumes (FLOW-RESUME-SESSION). While it waits, Ersa says the folder is being put back: in the composer's status line for a message, and in the archived note for a Resume.
3. **Ersa sweeps on its own.** When it starts, about every hour, and after a session is archived, Ersa removes each leftover workspace that holds no unsaved work and no ignored files, with its branch, and writes what it removed to the diagnostic log. It asks nothing and shows nothing.
4. **Old sessions archive themselves, when the user says so.** On the settings page, under Storage, **Archive inactive sessions** is Never, or after 1, 2, 7, 14 or 30 days. With a number chosen, the sweep archives each session with no activity for that long, and step 1 follows. It stops nothing: a session whose backend is still running is left however long it has sat idle. Ersa keeps a backend running until its session is archived or deleted or Ersa quits, and closing the window is not quitting (FLOW-CLOSE-AND-QUIT), so such a session is archived by the first sweep after Ersa next starts. A session another program has open is left too, and so is one Ersa can't date.
5. **The user cleans up the rest.** Under Storage, **Clean up inactive sessions** takes 30, 60 or 90 days. Ersa lists what it can remove, checking each item as it goes, in groups:
   - the folders of sessions with no activity for that long, and the folders kept after archiving because they hold unsaved work, each with its sessions' titles, its project and when it was last active;
   - leftover workspaces the sweep kept;
   - branches named `ersa/…` that no session uses;
   - folders in Ersa's worktrees folder that Ersa can't identify.
   Each item shows the space it frees, once measured, and what removing it loses: how many changed files, how many commits that exist nowhere else, and a repository of its own when the folder holds one. An item that loses nothing is ticked; so is a branch whose changes the base branch already holds, which says so. The rest are unticked, and ticking one is choosing to discard what it holds. One can't be ticked: a folder Ersa can't identify and could not measure in time (Variations).
6. The user chooses to clean up. Ersa asks once, naming how many folders and branches go and the space freed and, when a ticked item holds unsaved work, how many changed files and commits are lost for good; the confirming button then reads as discarding them.
7. The user confirms. Ersa removes the items one at a time, showing how far it is, and the user can stop it after the current one. A session whose folder was removed stays, with its conversation and its branch, and resumes as in step 2. When it is done Ersa says what it removed and what it could not, with why, and reads the list again.

## Variations and errors

- **The branch is gone** when a put-away workspace is put back, or is checked out in another folder: the resume is refused with the reason, and the session stays as it was, archived when it was. So it does when git won't make the folder again for another reason, such as a rebase of the branch under way in another folder: the resume then fails with git's own words.
- **While a folder is being put back**: forking, deleting or removing a session there, and removing the workspace, are refused for the moment, and stopping the message that waits for the folder stops the message at once and lets the folder come back (PROTO-CORE-API-R143, R145).
- **A folder is in use** when Ersa puts it away or removes it: Ersa tries as a delete does (PROTO-CORE-API-R113). When the sweep's tries fail it tells no one. A leftover is judged again by the next sweep. A folder that was being put away is by then partly gone and the sweep can no longer check what is left, so no sweep touches it again (FLOW-CLEAN-UP-R24): the session reads as any archived one, and what is left of its folder goes when the session is resumed, which makes the folder again. The Clean up list says an item could not be removed and why.
- **A folder holds a repository of its own**, a submodule's or a nested one (PROTO-CORE-API-R147 says which count): git removes such a folder only when forced, a submodule's own branches, stashes and history go with it, and Ersa can neither check all of that nor put it back. So Ersa never puts the folder away or removes it on its own: the session reads as any archived one, its folder stays, and the Clean up list shows the folder, says why it was kept and leaves it unticked. Removing it there, once the user approves, removes that repository too, and the folder comes back without it: whoever needs a submodule checks it out again.
- **Something changed after the list was read**: Ersa removes nothing of that item, shows it as it is now, unticked when it now holds unsaved work, and goes on to the next.
- **A session there is running, starting or being deleted**: its folder is not on the list, and is refused if it was.
- **A session shared with the backend's own tools**: a session started there counts as any other, so a folder is put away only when every session in it is archived or inactive.
- **A root workspace** is never put away, listed or removed: it is the user's own folder.
- **A session that is not archived** can be in a put-away workspace: one unarchived and not yet written to, or one whose folder the Clean up list removed. It reads as any stopped session, and its folder comes back when it is resumed.
- **Deleting a session whose workspace is put away** deletes no folder, since there is none, and deletes its branch or keeps it as a delete of any session does: the branch stays when another session uses the workspace (FLOW-ARCHIVE-DELETE-SESSION-R13 to R15).
- **Forking one** starts the fork's workspace from the branch, or the commit, the put-away workspace had checked out (FLOW-FORK-SESSION).
- **A leftover that holds ignored files** is kept for the list too: the sweep is Ersa's own, so it keeps more than an archive does.
- **Attachments copied into the folder** go with it. A message that named one still shows it in the transcript; the copy is not made again.
- **Ersa stops part way** through putting a folder away or removing one: a leftover is still a leftover, and the next sweep judges it again; a workspace that was being put away stays put away with what is left of its folder, as when the folder was in use.
- **The list can't be read**, or an item can't be checked: Storage says so with the reason, and an item that can't be checked is unticked and says its contents can't be counted.
- **A folder Ersa could not measure in time**: one of the folders it can't identify, too much to read to the end in 30 seconds. Ersa then can't tell whether anything in it changed after the list was shown, so it removes none of it: the list shows the folder and where it is, says that Ersa could not measure it in time and will not remove it, and gives no way to tick it. Whoever wants it gone deletes it themselves. A session's folder or a leftover that could not be measured only shows no size, since what removing it loses is counted another way.
- **Nothing to clean up**: Storage says so.

## Requirements

Putting away and putting back:

- ~~**FLOW-CLEAN-UP-R01**~~: retired 2026-11-25 (a folder that holds a repository of its own stays), see FLOW-CLEAN-UP-R22.
- **FLOW-CLEAN-UP-R22**: Core shall put an isolated workspace away when it is `ready`, at least one session uses it, every session that uses it is archived and none is live, starting or dormant, no session marked deleting refers to it, `workspace.changes` counts no `uncommitted` and no `stranded` and is not `unrecorded`, and its folder holds no repository of its own (PROTO-CORE-API-R147); it shall never put away a root workspace.
- **FLOW-CLEAN-UP-R02**: Putting a workspace away shall store what its folder has checked out (a branch, or a commit when it is on none) and set its state to `put_away` before anything is removed, then remove the folder and git's record of the worktree, keeping the workspace, its sessions and every branch.
- **FLOW-CLEAN-UP-R03**: When `session.resume`, or a send to a session that is not running, names a session whose workspace is `put_away`, Core shall put the workspace back before it checks the folder and before it starts the backend: it shall remove whatever stands at the path, which is what a put-away left unfinished, make the worktree at the same path as `workspace.create` makes one, with the stored branch checked out at its tip, or the stored commit, and set the state to `ready`.
- **FLOW-CLEAN-UP-R04**: When the stored branch or commit no longer exists, Core shall refuse the resume or send with `invalid_state` and reason `branch_gone`; when another worktree has the stored branch checked out, with reason `branch_in_use`; either way it shall leave the workspace `put_away` and the session as it was.
- **FLOW-CLEAN-UP-R20**: When git refuses to make the worktree again for any other reason, as it does for a stored branch that another worktree is rebasing or bisecting, Core shall refuse the resume or send with `vcs_error`, git's own words in `detail`, and shall leave the workspace `put_away` and the session as it was.
- **FLOW-CLEAN-UP-R05**: While a send waits for its session's workspace to be put back, `session.send_progress` shall report phase `putting_back`; the Shell shall keep a `session.resume` waiting for Core's answer for 10 minutes before it counts it unanswered.
- **FLOW-CLEAN-UP-R21**: While a Resume the user chose on the archived note is unanswered, the note shall say that the session's folder is being put back, in place of saying that the session is archived, from when Core reports phase `putting_back` for the session (PROTO-CORE-API-R146) until the resume is answered; a refused resume shall return the note to saying that the session is archived.

The sweep:

- **FLOW-CLEAN-UP-R06**: Core shall sweep when it starts, at least once an hour after that, and when a session is archived. A sweep shall check one workspace at a time, holding at most one of the places PROTO-CORE-API-R116 counts, and no request shall wait for a sweep except for its turn at a project's worktrees (PROTO-CORE-API-R118).
- ~~**FLOW-CLEAN-UP-R07**~~: retired 2026-11-25 (a folder that holds a repository of its own stays), see FLOW-CLEAN-UP-R23.
- **FLOW-CLEAN-UP-R23**: A leftover workspace is an isolated workspace that no session refers to and that was made at least an hour ago, except a `put_away` one with anything standing at its path or with git's record of a worktree there, which is what a put-away that failed part way left (R24). When `workspace.changes` counts no `uncommitted`, no `ignored` and no `unshared` and is not `unrecorded`, and its folder holds no repository of its own (PROTO-CORE-API-R147), the sweep shall remove its folder, git's record of the worktree, its branch unless another worktree has it checked out, and the workspace.
- **FLOW-CLEAN-UP-R08**: The sweep shall remove nothing that holds unsaved work and nothing it could not check, shall never delete a session, and shall write to the diagnostic log each workspace it puts away or removes and, the first time it keeps a leftover, why.
- ~~**FLOW-CLEAN-UP-R09**~~: retired 2026-11-25 (no sweep finishes a put-away that failed part way), see FLOW-CLEAN-UP-R24 and R25.
- **FLOW-CLEAN-UP-R24**: When a put-away the sweep began is refused, leaving the workspace `ready` (PROTO-CORE-API-R140, R147), the next sweep shall judge the workspace again as R22 says; when it fails after the workspace was stored `put_away` (PROTO-CORE-API-R141), no sweep shall try the put-away again or remove anything at the workspace's path. Either way Core shall tell no client.
- **FLOW-CLEAN-UP-R25**: When the removal of a leftover workspace that the sweep began fails, the next sweep shall judge the workspace again as R23 says, and Core shall tell no client.
- **FLOW-CLEAN-UP-R10**: While the setting `sessions.archive_inactive_days` is 1, 2, 7, 14 or 30, the sweep shall archive each session it lists that is not archived, pinned, unseen or marked deleting, that is not live or starting, that no connection is subscribed to, that the backend's live-session registry does not show open in another process, and whose last activity, else its creation, is at least that many days ago; unset, it shall archive none. It shall leave a session `session.set_archived` would refuse, one whose backend can't say whether another process has it open, and one with no last activity whose creation nothing remembers. The sweep shall stop no session.

The list:

- **FLOW-CLEAN-UP-R11**: `cleanup.list` shall list as `workspace` each `ready` isolated workspace with at least one session and none live, starting, marked deleting or dormant, whose sessions are all archived, or are all inactive for `inactive_days` with none pinned, unseen or subscribed to, a session with no last activity whose creation neither its record nor the app log dates never counting as inactive; as `leftover` each leftover workspace; as `branch` each local branch named `ersa/…` in a project's repository that no workspace names and no worktree has checked out; and as `folder` each folder in a project's folder under the worktrees root that no workspace and no git worktree record names.
- **FLOW-CLEAN-UP-R12**: `cleanup.inspect` shall report, for a `workspace` or `leftover`, what `workspace.changes` counts and the folder's size; for a `branch`, its `unshared` commits and whether merging it into the base branch would change nothing (`merged`); for a `folder`, its size; and a `token` that changes whenever what removing the item would lose changes. For a `folder` item whose measuring did not finish in its 30 seconds, it shall report no size and a `token` that differs on every inspect.
- **FLOW-CLEAN-UP-R13**: `cleanup.remove` shall put a `workspace` item away; remove a `leftover` item's folder, git's record, branch and workspace; delete a `branch` item's branch; and delete a `folder` item's folder. It shall refuse with `invalid_state`, removing nothing, when `token` differs from the item's token now, with the item as it is now in `detail`, and when removing the item would lose unsaved work, or the item is a `folder`, and `discard` is not true.
- **FLOW-CLEAN-UP-R26**: `cleanup.inspect` shall report, for a `workspace` or `leftover`, whether its folder holds a repository of its own (`holds_repository`, PROTO-CORE-API-R147), and the item's `token` shall change when that does.
- **FLOW-CLEAN-UP-R27**: `cleanup.remove` shall count removing a `workspace` or `leftover` item whose folder holds a repository of its own as losing unsaved work, refusing it without `discard` as R13 says; with `discard` it shall remove the folder with every repository in it.
- **FLOW-CLEAN-UP-R14**: Nothing in this flow shall delete a session or its record, change a root workspace, delete a branch on a remote, delete a local branch not named `ersa/…` that no workspace names, or delete a folder outside the worktrees root that no workspace names.

Storage:

- **FLOW-CLEAN-UP-R15**: Storage shall offer Archive inactive sessions as Never, 1, 2, 7, 14 or 30 days, showing the value in force, and shall write the choice to `sessions.archive_inactive_days`, Never clearing it.
- **FLOW-CLEAN-UP-R16**: The Clean up list shall show each item with what it is, its sessions' titles and project where it has them, the space it frees once measured, and how many changed files and commits that exist nowhere else removing it loses; it shall tick by default exactly the items whose removal loses no unsaved work and the `branch` items reported `merged`, and never a `folder`.
- **FLOW-CLEAN-UP-R28**: The Clean up list shall say of an item reported `holds_repository` that its folder holds a repository of its own, which goes with the folder and does not come back with it, and shall count the item as one whose removal loses unsaved work, so it is unticked by default (R16); when one is ticked, the question R17 asks shall say how many of the folders that go hold one.
- **FLOW-CLEAN-UP-R29**: The Clean up list shall show a `folder` item reported without a size as one Ersa will not remove, saying that it could not be measured in time and where the folder is, and shall give no way to tick it.
- **FLOW-CLEAN-UP-R17**: Ersa shall remove nothing on the list before the user confirms one question that names how many folders and branches go, the space freed and, when a ticked item holds unsaved work, how many changed files and commits are lost for good.
- **FLOW-CLEAN-UP-R18**: After the user confirms, Ersa shall remove the ticked items one at a time, show how many are done, stop before the next item when the user stops it, say for each item it could not remove why, and read the list again when it ends.
- **FLOW-CLEAN-UP-R19**: Storage shall say that it is checking while the list is read and each item until it is inspected, that there is nothing to clean up when the list is empty, and why when the list can't be read or an item can't be inspected, leaving that item unticked.

## Out of scope

- Selecting several sessions and archiving or deleting them at once. The owner wants it (2026-11-21), it is what removes old sessions' branches, and it gets its own planning pass.
- Archiving a session when its pull request closes: Ersa knows nothing of pull requests yet.
- Archiving a session and keeping its folder, which Claude Desktop's "by default" implies it can do.
- A breakdown of what Ersa uses on disk.
- A session with no record that a start cut off after `session.create` left in the rail: the user deletes it.
- Removing a project, and rotating the diagnostic log while Ersa runs.
- What a backend keeps about a folder Ersa removed (ADR 0033).

## Open questions

- Whether Clean up should remove a folder it can't identify and could not measure in time. Today it won't (R12, R29), so the stray folders that take the most space are the ones a person must delete outside Ersa, and every reading of the list spends 30 seconds on each. Claude Desktop skips a session whose worktree could not be checked unless the user asks for that work to be discarded too (`claude-desktop/cleanup-2026-11-20.txt`), which leans toward removing such a folder on the person's word, saying plainly that Ersa could not measure it or tell whether it changed after it was listed. That would give up the check R13 makes of every other removal and the space R17 names. Giving the measuring more time is the third way: slower, and still bounded. The owner's to decide.
- Whether an hour is the right bound before a workspace no session uses counts as a leftover. It only has to outlast the moment between making a workspace and starting its session.
- Whether a folder that holds ignored files Ersa did not make, such as local configuration that was never committed, should be kept as one that holds unsaved work is (ADR 0038, Consequences). A nested repository that is ignored is among them: it goes with the folder as any ignored file does, whatever it holds.
- What a put-back, and a delete, should do with what a put-away that failed part way left at the workspace's path. Today a put-back removes it without a check (R03), and a delete of the last session there removes it too, though the delete question says the folder is already removed (FLOW-ARCHIVE-DELETE-SESSION-R13) and PROTO-CORE-API-R123 says such a delete deletes no folder. Anything written there after the put-away began is lost without a question, which ADR 0038 does not allow of a removal the user was not asked about. Core can't tell such files from the put-away's own: a half-removed folder's ignore rules may have gone with its files, and git's record with them.
- Whether a removal should first move the folder out of the way, so that one that fails part way leaves nothing at the workspace's path, and what it left can be deleted later without a check. That would let the sweep finish a put-away, which it does not do (R24), and would answer the question above.
- Whether what a failed put-away left should be on the Clean up list. Today nothing shows it, and it stays until the session is resumed or deleted. When its sessions are removed instead, the workspace is no leftover (R23), since a `put_away` workspace's counts do not see what stands at its path, so neither the sweep nor the list removes it, and it stays for good.
- Whether Ersa should put away a folder that holds a submodule when the submodule holds nothing of its own, and check the submodule out again when it puts the folder back, which needs the network. Today such a folder stays until the user removes it from the Clean up list.
- Whether Ersa should say, on an archived session, that its folder was kept and why. Today only the Clean up list does.
- What Claude Desktop does when a resumed session's branch is gone. The fixture did not observe it; Ersa refuses with the reason.
